# SF-1 — Initialize SkillFlow project

> Source: [SF-1](https://bendak.youtrack.cloud/issue/SF-1) · Specs: SF-A-2 (Persistence v0), SF-A-3 (Execution Boundary v0), SF-A-5 (Command Contract v0), SF-A-6 (Implementation Plan v0)

## Context

The `skill-flow` repository currently contains a single `README.md` and nothing else — no package, no build config, no tests. Every other Wave 1 issue is blocked on this one: SF-2 (domain types) and SF-3 (workspace + SQLite) both declare SF-1 as their only dependency, and the whole 39-issue backlog sits behind them.

SF-1 is deliberately narrow: stand up a Python project that installs, tests, and starts, plus declare the `.skillflow/` storage convention. It implements no lifecycle behaviour. The value is that the next session can write domain types and persistence without first arguing about packaging, layout, or the test runner.

Stack decisions confirmed with the user: **uv + hatchling**, **argparse**, **pytest + src layout**, **ruff**.

## 1. Objective

Produce a locally installable `skillflow` Python package with a working executable entry point, a running test suite, and a declared `.skillflow/` directory convention — satisfying SF-1's acceptance criteria (installs locally; tests run; executable starts; no external services) with the smallest implementation that does so.

## 3. Proposed approach

A conventional single-package `src` layout driven by `pyproject.toml`:

- **hatchling** as build backend, **uv** for environment and lockfile. `uv sync` on a fresh checkout produces a working dev environment with zero manual steps.
- **Zero runtime dependencies.** argparse and sqlite3 are stdlib. PyYAML arrives with SF-8 (workflow loader), not now.
- **argparse CLI** exposing only `--version` and `--help`. The four lifecycle commands (`resolve-task`, `prepare-artifacts`, `complete-run`, `decide`) are owned by SF-19/SF-21/SF-25/SF-27 and are **not** stubbed here.
- **`.skillflow/` convention as constants only** — directory and file names, no filesystem I/O and no root detection. Detection, creation, and SQLite initialisation are SF-3's explicit deliverables.
- **pytest** with `src` layout so tests exercise the installed package, which is exactly what the "clean test run on a new checkout" DoD asks for.
- **ruff** for lint + format, configured with a narrow rule set so later issues do not inherit churn.

Version is single-sourced from `src/skillflow/__init__.py` via hatchling's dynamic version, so `pyproject.toml` and `__version__` cannot drift.

## 5. Detailed implementation steps

1. **`pyproject.toml`**

   ```toml
   [build-system]
   requires = ["hatchling"]
   build-backend = "hatchling.build"

   [project]
   name = "skillflow"
   description = "Lightweight lifecycle orchestration for independent Claude Code runs."
   readme = "README.md"
   requires-python = ">=3.11"
   dynamic = ["version"]
   dependencies = []

   [project.scripts]
   skillflow = "skillflow.cli:main"

   [dependency-groups]
   dev = ["pytest>=8", "ruff>=0.6"]

   [tool.hatch.version]
   path = "src/skillflow/__init__.py"

   [tool.hatch.build.targets.wheel]
   packages = ["src/skillflow"]

   [tool.pytest.ini_options]
   testpaths = ["tests"]
   addopts = "-q"

   [tool.ruff]
   src = ["src", "tests"]
   target-version = "py311"
   extend-exclude = ["*.md"]   # Run artifacts are Markdown; the formatter must not own them

   [tool.ruff.lint]
   select = ["E", "F", "I", "UP", "B"]
   ```

   `requires-python = ">=3.11"` is the floor because SF-2 will want `enum.StrEnum` for the status types.

2. **`src/skillflow/__init__.py`** — module docstring plus `__version__ = "0.1.0"` (matches the issue's Fix version 0.1.0). Nothing else; no re-exports to maintain.

3. **`src/skillflow/cli.py`**

   - `build_parser() -> argparse.ArgumentParser` with `prog="skillflow"`, a one-line description, and `--version` via `action="version"` rendering `skillflow {__version__}`.
   - `main(argv: list[str] | None = None) -> int`: parse `argv` (defaulting to `sys.argv[1:]`); with no arguments, print help to stdout and return `0`; otherwise return `0`.
   - Return an int rather than calling `sys.exit` — keeps `main` directly testable and lets later issues map lifecycle errors onto exit codes without restructuring.
   - Do **not** add `add_subparsers()` yet. An empty subparser container is a placeholder for a contract that has not been designed; SF-19 adds it together with the first real command.

4. **`src/skillflow/__main__.py`** — `from skillflow.cli import main`, then `raise SystemExit(main())` guarded by `if __name__ == "__main__":` so that *importing* the module (package walkers, coverage, doc tools) does not execute the CLI and exit the interpreter.

5. **`src/skillflow/workspace.py`** — module docstring reproducing the SF-A-2 §2/§5/§7 layout, then constants only:

   ```python
   WORKSPACE_DIR_NAME = ".skillflow"
   DB_FILE_NAME = "skillflow.db"
   ARTIFACTS_DIR_NAME = "artifacts"
   RUNS_DIR_NAME = "runs"
   ```

   Documented layout:

   ```text
   <repo-root>/.skillflow/
   ├── skillflow.db      # lifecycle state, metadata, events
   ├── artifacts/        # durable artifact content
   └── runs/<run-id>/    # per-run diagnostics (output.log), retained mainly on failure
   ```

   No functions, no `Path` construction, no `mkdir`. SF-3 owns repository-root detection, workspace creation, idempotent setup, and SQLite initialisation.

6. **`.gitignore`** — as listed in §4. Ignoring `.skillflow/` here is a local decision for *this* repository (SkillFlow dogfooding itself); SF-A-2 §3 explicitly leaves the commit/ignore question open for target repositories, so do not ship a `.gitignore` template or claim a global rule.

7. **Tests** (see §8).

8. **`README.md`** — append a Development section with the four commands from §14 and a Storage layout block matching step 5. Keep it short; full documentation is SF-39.

9. **Generate the lock and verify** — run `uv sync`, then the checks in §14. Commit `uv.lock`.

## 6. Domain/data model changes

**None.** SF-1 introduces no domain entity, no status enum, no persistence schema, and no lifecycle semantics. Task, Run, Result, Artifact, WorkflowDefinition, HumanDecision, and LifecycleEvent are SF-2's deliverables; their tables are SF-4's.

`workspace.py` names storage locations only. Naming where the database will live is not a data model.

## 7. API/command changes

The `skillflow` console script is introduced with this surface and no more:

```text
skillflow --version   → "skillflow 0.1.0", exit 0
skillflow --help      → usage text, exit 0
skillflow             → usage text, exit 0
skillflow <unknown>   → argparse error on stderr, exit 2
```

`python -m skillflow` is equivalent to `skillflow`.

The `/skillflow:*` Claude Code slash commands from SF-A-5 are **not** created here — they belong to SF-29 (Claude Code commands) and SF-28 (operational protocol), and each underlying lifecycle command has its own issue.

## 8. Test strategy

`tests/test_cli.py`

- `main(["--version"])` exits `0` (argparse's `version` action raises `SystemExit(0)`; assert via `pytest.raises(SystemExit)`) and prints text containing `f"skillflow {__version__}"` — interpolating the imported `__version__` rather than hard-coding `0.1.0` keeps the test honest across version bumps while still pinning the `skillflow ` prefix that §7 fixes.
- `main([])` returns `0` and writes usage containing `usage: skillflow` to stdout (capsys).
- `main(["--help"])` exits `0`.
- `main(["definitely-not-a-command"])` exits `2`.

`tests/test_workspace.py`

- Assert each of the four constants equals its expected literal. This is a deliberate change-detector: the directory name is a published convention that SF-3 and every later issue depend on, so silent drift should fail loudly.

`tests/test_entry_point.py`

- Subprocess test: `subprocess.run([sys.executable, "-m", "skillflow", "--version"])` returns `0` with `skillflow {version}` on stdout. This proves the packaged entry point actually starts — SF-1's third acceptance criterion — without depending on `PATH` resolution of the console script inside the test session.
- Second subprocess test: `python -m skillflow` with no args returns `0` *through* `main()`'s `return 0` (not via argparse's `SystemExit`), exercising the exit-code propagation path that `--version` bypasses.

Not tested automatically: that the `skillflow` console script itself is on `PATH`. That is verified manually in §14; asserting it in-process would test uv's shim rather than this package.

## 9. Edge cases and failure scenarios

| Scenario | Handling |
| --- | --- |
| Version drift between `pyproject.toml` and `__init__.py` | Impossible — hatchling reads `__version__` from `src/skillflow/__init__.py` (`dynamic = ["version"]`). |
| `python -m skillflow` and `skillflow` diverge | `__main__.py` delegates to the same `cli.main`; covered by the subprocess test. |
| Tests import the working tree instead of the installed package | `src` layout plus `uv run pytest` (which installs the project into the environment) makes the working tree non-importable by accident. |
| Bare `skillflow` looks like a crash | Prints help and exits `0` rather than erroring — "executable starts" should be observable with no arguments. |
| Fresh checkout on a machine without Python 3.11 | uv downloads the interpreter named in `.python-version` automatically; no manual setup. |
| Network unavailable | No runtime dependencies, so the installed CLI never needs the network. `uv sync` needs the index once to fetch pytest/ruff — note this in the README rather than vendoring anything. |
| External services | None introduced. sqlite3 is stdlib and is not even touched in SF-1. |
| `main()` returning non-zero later | Signature already returns `int`; `__main__.py` and the console script both propagate it. |

## 10. Architectural constraints

Checked against the SkillFlow boundaries:

- **Claude Code is the execution layer** — SF-1 adds no execution capability whatsoever.
- **SkillFlow owns durable lifecycle state** — none is created yet; the `.skillflow/` convention only names where it will live.
- **Runs are independent and bounded** / **Artifacts are the durable context** — no Run or Artifact code in scope.
- **Lifecycle and Context Selection are deterministic** — no evaluation logic in scope. The CLI is pure argument parsing.
- **Workflow Definition is not a runtime entity** — not touched.
- **No Router / Transition / Loop / Iteration / Rework / Handoff / Workflow Instance entities** — none introduced; `workspace.py` holds four string constants and no types.
- **SkillFlow does not automatically launch Claude Code** — the CLI spawns no processes.
- **The next Run is never created in the current session** — no Run creation exists.

Two boundary risks worth naming explicitly, both avoided by this plan:

1. **Stubbing the four lifecycle subcommands** in `cli.py` "so the structure is there". This would leak SF-19/21/25/27 scope and, worse, freeze a command contract before SF-A-5's preconditions and error types are implemented. Excluded.
2. **Implementing repository-root detection or `.skillflow/` creation** in `workspace.py`. SF-3 lists "predictable repository-root detection, workspace initialization, SQLite initialization, idempotent setup" as its deliverables; doing any of it here duplicates that issue and risks a competing API. Excluded — constants only.

## 12. Definition of Done

On a clean clone with only `uv` installed:

1. `uv sync` completes and creates `.venv` with pytest and ruff.
2. `uv run pytest` passes with all tests collected from `tests/` and no warnings-as-errors surprises.
3. `uv run skillflow --version` prints `skillflow 0.1.0` and exits `0`.
4. `uv run python -m skillflow --version` prints the same and exits `0`.
5. `uv run ruff check .` and `uv run ruff format --check .` are clean.
6. No network access is required by the CLI itself, and no external service is contacted at any point.
7. `uv.lock` is committed; `.venv/`, caches, and `.skillflow/` are ignored.

## 13. Risks / open questions

| Risk / question | Assessment |
| --- | --- |
| `.python-version` pinned to `3.11` while the machine runs 3.14 | Deliberate: developing on the supported floor catches accidental use of newer syntax before it reaches a user. Cost is a one-off interpreter download by uv. Flip to `3.13`/`3.14` if that friction is unwelcome — a one-line change. |
| ruff rule set may be too narrow or too broad | Starting with `E, F, I, UP, B` is conservative. Widening later is cheap; a broad set now would generate churn across every subsequent issue. |
| Committing `uv.lock` | Correct for an application-shaped project (SkillFlow is a tool, not a library others depend on). Revisit only if SkillFlow is ever published as a library. |
| `.skillflow/` gitignored in SkillFlow's own repo | Local choice, per SF-A-2 §3 which leaves this open. It prevents dogfooding state leaking into commits. Does not bind target repositories. |
| Bare `skillflow` exiting `0` with help | A judgement call; some CLIs exit `2`. Exit `0` reads better against "executable starts" and is trivially changed once real subcommands exist. |
| Test asserting exact constant values is a change-detector | Intentional. The `.skillflow` name is a cross-issue contract, not an implementation detail. |
| Open question for the user | Should `skillflow` eventually be installed globally (`uv tool install`) for use inside *other* repositories? Not needed for SF-1, but it will shape SF-3's root detection. Worth deciding before SF-3 starts. |
